# 2026-11-15 Mazer slice H4 (pure core): contact, rewind, Sentry motion

- WHAT changed: three new pure modules in `src/mazer-core/hazards/`, re-exported from the hazards index only (not from `src/mazer-core/index.ts`). `contact.ts` is the collision phase (occupancy and head-on swap, wrap swaps included), the invulnerability counter (N = 4 in play) and the CLEAN mark. `rewind.ts` plans the rewind after a contact (contract A2) and holds the runtime rewind-safety check. `sentry.ts` is Sentry motion: at most 4 shuttles, each cell a pure function of its spec and the tick. No scene, renderer or worker calls any of them yet; H3's wiring calls them after H3 merges.
- WHY it changed: roadmap slice H4. The contact rules must be proven equal to the validator's before anything moves on screen.
- Rule: play and validator share one contact definition. `stepCollision` gives the same answer as the validator's transition relation (`createHazardStateSpace(...).forEachSuccessor`) on every step (tested on random walks), and a witness that steps across a wrap into a swapping Sentry is rejected by `verifyWitness` as `contact-swap` and flagged by the tracker as `swap`.
- Rule: the rewind cell is the last junction on the player's own trail that lies strictly behind the contact. A junction equal to the contact cell is skipped, so a contact on a junction never rewinds in place. If that junction has no route to the goal at N = 4, the previous trail junction is tried (at most 2 tries, `REWIND_JUNCTION_TRIES`), then the validated start.
- Rule (never strands): when even the start has no route at this tick, the plan is `start-rescue`: it lengthens invulnerability to the smallest value that works (the waits at the start until its N = 0 route opens). This is only possible when the start is open on every tick of the wait, and `canAlwaysRescue` says so per level at build time. It can only make a level easier, so it invalidates no verdict. `stranded` exists only for a level whose start is sealed in, which the H2 overlay never ships (tested on 10,000 contacts on shipped levels: 0 stranded, 0 rescues needed).
- Decision: the "runtime A* witness" of A2 is built as an exact table lookup, not a per-contact A*. Reasons: an A* from an unsolvable state explores the whole state space (worst case not bounded under 2 ms, and it allocates), while one reverse BFS from the goal at build time gives the exact N = 0 distance of every (cell, tick mod P) state, and the N = 1..4 layers are a bounded recursion over it (at most 5^4 lookups, no allocation). `distanceFrom` equals `findWitnessRoute` (solvable and witness length) on every sampled state, k = 0..4.
- API (stable from this PR; a shape change is a contract change):
  - `createContactTracker()` gives `stepCollision(tick, cell, dest, enemiesAtT, enemiesAtT1, enemyCount): HazardContactEvent | null`, `grantInvulnerability(ticks)` (never lowers), `invulnerableTicks`, `contacts`, `clean`, `summary(): { contract: 'mazer-hazard-contact-v1', contacts, clean }`, `reset()`. The event object is reused (copy it to keep it). `findOccupancyContact` and `findSwapContact` are the two raw rules. `PLAY_INVULNERABLE_TICKS = 4`.
  - `createRewindPlanner(graph, timeline, { start, goal, invulnerableTicks? })` gives `planRewind(trail, length, tick): HazardRewindPlan` (`outcome`, `cell`, `trailIndex` (-1 means reset the trail to the start), `retractedCells`, `tick` (the clock is held), `invulnerableTicks`, `routeTicks`, `junctionsChecked`; one reused object), `distanceFrom(cell, tick, k)` (-1 when no route), `canAlwaysRescue`, `period`. Build it once per level, off the hot path (the maze worker or level start).
  - `createSentryField(graph, specs)` gives `count` (at most `MAX_SENTRIES = 4`, more throws), `period`, `cellAt(index, tick)`, `writeCellsAt(tick, out)` (fills a caller buffer, returns the count, no allocation), `rail(index)`. Positions equal `timeline.enemyCellsAt` for every tick, negative ticks included.
- Evidence (node 1x on a desktop PC, shared and memory-starved during the run):
  - Property: 10,010 random contacts (random-walk trails up to 240 steps, random ticks) on 19 shipped levels (25x51 and 45x27, levels 20..288 with Sentries): 0 stranded; 8,934 junction, 1,079 start (trails with no usable junction behind them), 0 previous-junction, 0 rescue. Every non-rescue rewind state was checked by an independent oracle (`computeSolvableStates` at N = 4).
  - `planRewind` worst case 0.023 ms, asserted under 2 ms (min of 3 runs per contact, 200 contacts per level on the same 19 levels). Planner build on 180 shipped levels (L10..300, 3 seeds, both boards): median 1.10 ms, p95 3.98 ms, worst 29.17 ms; largest period 40; tables keep 6 bytes per (cell, tick) state plus a 4-byte BFS queue during the build, at most 0.49 MiB peak.
  - Exactness: `distanceFrom` equals `findWitnessRoute` on over 3,000 sampled (cell, tick, k) states of 24 random wrapped 11x11 mazes with random gates and Sentries, including over 50 unsolvable ones.
  - Demo: the overlay's stored witness replays with zero contacts through the tracker on 10+ real levels.
- Status: built, flag off, not called. Flag-off play and the golden ladder are unchanged because nothing imports these modules outside the hazards folder and its tests. NOT checked: phone CPU timing; wiring, rendering, the 250 ms retract animation and the 2 Hz blink (H3 follow-up); real-device play.
