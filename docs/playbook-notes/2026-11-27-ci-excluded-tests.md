# CI excluded tests: three of the five now run in the required check

- WHAT changed: `tests/maze/maze-soak.test.ts` is no longer excluded; the whole `tests/maze` folder run in job `verify` runs it. `tests/analysis/live-auth-persistence-soak.test.mjs` and `tests/ui/dom-settings-primitives.test.ts` run in a new step ("Verify the tests that need Playwright Chromium") placed right after "Install Chromium ..." in job `verify`; they stay excluded from the folder run so nothing runs twice. `scripts/verify/check-test-coverage.mjs` knows the exclusion category `run after browser install`: such a file counts as run, must be run only inside job `verify` and only in a step after a `playwright install` step, and the entry is stale if no step runs it. The two root `playbook-*` tests stay excluded, now with the category `local sibling checkout`.
- WHY it changed: the soak failed on main at line 181 (`finalNearLowerBand`) with no real growth. A vitest worker thread is not started with `--expose-gc`, so `globalThis.gc` was undefined, the "collect before sampling" helper did nothing, and the samples were raw heap sizes (42 MB final vs a 15 MB minimum). The test now exposes the collector itself (`v8.setFlagsFromString('--expose-gc')` + `vm.runInNewContext('gc')`). No assertion or threshold changed and no `src/` code changed. The two browser tests need only a local Chromium and a loopback server (no network account, no credentials); they passed locally.
- Rule: fix a failing test's measurement, never its thresholds; a test that needs the browser runs after the install step in the required job, via the `run after browser install` category, not by dropping it from CI. A test that reads another repo's files stays excluded with that exact reason: a committed copy would freeze the "live contract" it claims to compare, which is not coverage.
- Evidence: before, `npx vitest run tests/maze/maze-soak.test.ts` failed twice (finalHeapUsed 42265216 / 44450992, finalNearLowerBand=false) and passed with `NODE_OPTIONS=--expose-gc`; after, it passed 4 of 4 runs (default, threads with 4 workers). The two browser files: 18 and 38 tests passed locally. Negative controls on the new check: browser file also run in the folder step (fails: misplaced + run twice), browser step removed (fails: stale), browser step before the install step (fails: misplaced). CI log lines for the new step: see the PR body.
- Status: in review. The two playbook tests remain excluded: `playbook-adoption-evidence` compares the Mazer export with `../playbook/exports/playbook.contract.example.v1.json`, `playbook-verification-report` validates against `../../schemas/atlas.playbook.verification.report.v1.json` (ATLAS root). ## Also in this change: four hardening notes from the #736 review (scripts/verify/check-test-coverage.mjs)

1. Step splitting works on any list item at step indent (`- name:`, `- run:`, `- uses:`, `- id:`, `- if:`), so a bare `- run:` step is no longer merged into the previous step.
2. A counted test step in job `verify` with `if:` or `continue-on-error` (step level, or job level `if:` / `continue-on-error`) is reported, and does not count as protection (`continue-on-error: false` is allowed). No existing step in verify.yml has either.
3. A folder operand under a listed folder (for example `tests/reset/sub`) is treated as listed.
4. The usage docstring names the folder-run-outside-job, required-file-outside-job, conditional-step and browser-order failures.
New unit tests `tests/architecture/test-coverage-check.test.mjs` (9 cases, each negative case has a plain-step control); the real-workflow negative control (`continue-on-error: true` on the folder step) made the check fail and was reverted.

## Review round 2 (HOLD on the first version of the hardening), fixed on the same branch

- P1: the job-level `if:` / `continue-on-error` check was dead on the real verify.yml. Its header regex started at the `on:` block key `  pull_request:`, so the verify job was stored under the key "pull_request". Probe (real file with `continue-on-error: true` injected at job level, `conditionalRequiredSteps` count): before 0, after 9. The parser now reads only what follows `jobs:`. The browser-step rule ("run only inside job verify, after the install step") used a separate job lookup that did start at `jobs:`, so it was correct, not working by accident; it is now pinned by a test on the real workflow text.
- P3: the Chromium-install flag resets per job; quoted keys (`"continue-on-error": true`, `'if': false`) are found; a trailing comment on a value is ignored (`continue-on-error: false # x` is fine); a `- run:` line inside a `run: |` block body is body text, not a step; a flow-style step (`- { run: ... }`) that carries a test command is reported as an unsupported form. `maze-soak` asserts first that the collector was set up (no threshold or band change).
- Limits of the hand parser (it is not a YAML parser): it reads this repo's workflow shape only (2-space jobs under `jobs:`, a block-style `steps:` list, keys at dash indent + 2). Anchors/aliases, flow-style jobs and multi-line flow values are not understood; the real-workflow tests fail loudly if verify.yml stops binding steps to job `verify`.
- Tests: 16 cases in `tests/architecture/test-coverage-check.test.mjs`, including three on the real verify.yml text (steps bind to `verify`, none conditional; job-level injection is a finding; step-level injection is a finding). Fixtures now carry an `on:` block.
