- WHAT changed: MAZER-PERF-017 look restore. The game's Star Dust trail paints with the full painter again (`drawStarDustTrailFullToCanvasContext`, the painter before #706): every layer of the whole trail is repainted at the real breath, width and glow on every paint, so the whole trail breathes and twinkles together. `drawStarDustTrailToCanvasContext` in `src/render/starDustTrailCache.ts` (the name MenuScene imports) now routes to it; MenuScene changes by one comment only. The cached painter (C + A, #706/#710) is withdrawn from the game and kept as `drawStarDustTrailCachedToCanvasContext` for the trail-cost options page, whose 'CA' row installs it through the override seam; the page's default row is now Before (the game's painter).
- WHY it changed: Zac, 2026-11-25: "i hate how the player trail now has parts blinking slower and allat it looks bad, is there no other way to help w the lag issue without losing visual quality?" The brief: restore the pre-cache look exactly (target: max channel difference <=3 vs the full painter at 393x851 @2.625, Chromium and WebKit) and keep the lag win only if a cached design can meet that.
- Rule: a cached trail layer can only match a live trail if every layer it caches is still between two consecutive paints. Star Dust's are not: measure the layer's paint-to-paint change before designing a cache, and if it is above the pixel target, the cache is a look change, not an optimisation.
- Evidence: `scripts/analysis/check-star-dust-trail-exact-look.mjs` (new) records the real paints on the real scene (previewLevel 300, a ~600-tile trail, 3.2 s idle + 2.5 s walking) and compares off screen, composited over the board colour. #710 cache vs full painter: max channel difference 247 (Chromium) / 246 (WebKit); 61% / 64% of lit pixels off by more than 3, 34% / 40% by more than 16. How much each full-painter layer changes between two consecutive paints (any cache of that layer is at least this stale): bloom 39 / 66, thread 49 / 60, sparkles 209 / 245. Bloom cached at breath trough and peak and cross-faded, with zero staleness: max 25 / 28 (6.7% of pixels over 3). So no cached design meets <=3; the full painter meets it by construction (unit test: the game draw issues the same canvas calls as the full painter, and the cache is never touched). Cost per paint (raster flushed, recorded paints): full painter 48-51 ms Chromium, 83-89 ms WebKit; #710 cache 26 / 23 ms. Whole-frame headless meter on the real game, same run: Chromium 27.5 ms mean (full) vs 21.9 ms (cache) at 2.625x, WebKit 130 ms vs 100 ms at 2.625x and 99 ms vs 82 ms at 3x. So the look costs about 20-30% of a frame on a long trail; on short trails (under 48 tiles) the cache was already painting whole, so nothing changes there.
