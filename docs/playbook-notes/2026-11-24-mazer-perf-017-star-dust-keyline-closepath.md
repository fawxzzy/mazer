- WHAT changed: MAZER-PERF-017 (phone lag with a long trail). `src/render/starDustTrailCanvas.ts` now builds the star-dust sparkle keylines as `Path2D` batches of 64 sparkles joined with `addPath` (no transform) and strokes that one path once, instead of tracing every sparkle into the context path and stroking it. Same verbs, same points, same order, one stroke: the pixels are identical. Without `Path2D` (Node tests) it falls back to the old context path. New test `tests/architecture/star-dust-keyline-batching.test.ts` pins that the batched path equals the old path op for op and that no single path is closed more than 64 times. New probes: `scripts/analysis/profile-frame-phases.mjs` (per-phase frame time, per-object render time, 2D call counts, canvas sizes and a CPU profile under CDP CPU throttle; `--ab=path2d` measures the same page with the old and new keyline path; `--engine=webkit` runs without throttle or profile) and `scripts/analysis/check-star-dust-keyline-equivalence.mjs` (pixel diff of the real module, old vs new, at device scales 3, 2.625, 2.36 and 2; exits 1 on any difference).
- WHY it changed: Measured, not guessed. Level 300 at 390 x 844 @3 with 4x CPU throttle in Chrome: the frame was almost all trail rebuild, and the CPU profile's largest single entry was the browser's own `closePath` (229 ms per walk frame, about half of the frame). Chromium's `closePath` costs time in proportion to the path it closes, so one path holding about 2000 sparkle outlines is quadratic in trail length: 250 sparkles 1.5 ms, 1000 14.5 ms, 2000 46.6 ms, 4000 161.5 ms, versus 5.8 ms for 4000 without the close (Chrome 158, unthrottled). Building the same path in 64-sparkle pieces keeps every close cheap.
- Rule: Never close thousands of subpaths in one canvas path (context or Path2D) in Chromium. Build them in small `Path2D` batches and `addPath` them into one path, then stroke once: same pixels, linear cost. Measure frame phases with `profile-frame-phases.mjs` under throttle before picking a fix; the cost was in a native canvas call that no op-count budget sees.
- Evidence: Same page, same 496-tile trail, Chrome 4x throttle, `--ab=path2d`: idle frame mean 122.4 to 79.9 ms (trail rebuild 65.2 to 25.3 ms per frame), walk frame mean 258.3 to 215.7 ms (trail rebuild 181.0 to 118.7 ms per frame), `closePath` self time 101.5 ms per walk frame to below the top 12. Pixel diff of the real module at scales 3, 2.625, 2.36 and 2 (1909 sparkles): 0 channels differ. WebKit (Playwright build 2311 on Windows, a proxy for Safari, not iOS): `closePath` is NOT quadratic there (2000 sparkles 53 ms old vs 50 ms new), pixel diff 0, and the in-app WebKit timings were too noisy to show a change, so the gain is expected on Chromium/Android and not on iPhone. What is left after this, ranked from the Chrome profile: the bloom pass (about 44 ms per walk frame), the per-sparkle fill loop and its colour strings (about 31 ms), the thread strokes (about 14 ms), Phaser render (about 14 ms). The animated sparkles rebuild the whole trail about every other idle frame; making that cheaper changes pixels and needs an options page and Zac's pick. Nothing checked on a real phone.
