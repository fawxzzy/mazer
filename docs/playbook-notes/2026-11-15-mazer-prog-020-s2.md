# 2026-11-15 MAZER-PROG-020 S2 board scale grows slowly with the level (38 toward 40)

- WHAT changed: `resolveLegacyBoardScaleForLevel(level)` in `src/legacy-runtime/legacyBoardScale.ts` is now `S(L) = 38 + 2*(L-1)/((L-1)+200)`, rounded to 1e-4: 38 at level 1, 39 at level 201, 39.67 at level 1000, strictly increasing, never reaches 40. Largest step between adjacent levels is 0.01 (`LEGACY_BOARD_MAX_SCALE_STEP`), at level 1. The scale is now fractional, so the lifecycle clamp and `resolveLegacyProgressionScaleDetail` no longer round it to an integer; the grid still comes from the one rounding rule (`resolveLegacyBoardDimensions`) and the generator's odd-axis rule, so the played grid only moves when the rounded, odd-normalised width or height moves. The 10 px floor is now a per-device ceiling (`legacyBoardPlan.ts`, a cached walk down the 0.05 scale lattice): the result is `min(level scale, ceiling for this box)`, which keeps the final scale monotone over levels on every device (a plain "step down until it fits" was not monotone because tile px is not monotone in fractional scale). Golden `tests/fixtures/progression-ladder-golden.v1.json` regenerated again: only the hashes from level 255 up changed (the grid steps once the level scale passes 39.1), levels 1..254 are identical to S1. Trail-corner raster baselines were regenerated in S1 (smaller tile), not again here.
- WHY it changed: owner request (Zac, 2026-11-15): only a SLIGHT size increase over progression, never beyond 40; no camera, scroll, follow or zoom (the whole board always fits); no leaderboard reset and no level reset (level numbers and stored progress are untouched; receipts still record max(width, height)).
- Rule: board size is a function of the level, never of the device. Over levels 1..1000 the scale is monotone with step <= 0.0101. The realized cell grid is NOT guaranteed monotone: the layout aspect ratio is refined with a real layout pass, so on a few devices the across count can step back by 2 columns for some levels (for example 320x568 menu, 375x667 play). Rows and area still grow. Not fixed here (MenuScene is a hot file). The 10 px floor fires only where 10 px is physically impossible: on the 320 wide menu surface from about scale 38.5; the 320 wide PLAY surface and every wider phone hold 10 px up to 40 at these sizes.
- Evidence: `tests/reset/legacy-board-scale.test.ts` (curve endpoints, monotone, step bound over 1..1000, never above 40, device independent, floor ceiling monotone, 12 tests); `progression-ladder-report.ts --levels=1..300 --seeds=6 --assert` passes; real-layout dims per level in `tmp/seq.ts` style sweep: 390x844 play 27x53 (L1) -> 27x55 (L326); 360x780 play 25x55 -> 27x55 -> 27x57 (L363); 320x568 play 27x51 -> 29x51 (L39) -> 29x53 (L222). Not checked on a real phone; headless safe area is 0.
- Status: ladder tables still NOT retuned (S3). At the level-1000 scale the measured ceiling and felt saturation are above the baked `GEOMETRY_BUDGET_CEILING` 930 / saturation 283 (calibrated at scale 35; see the S1 note for the file list), so late-level blank patches stay larger until S3 re-baselines.
