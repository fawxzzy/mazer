# 2026-11-15 Mazer slice H2: hazard generation overlay (allocator + validators)

- WHAT changed: new pure modules `src/mazer-core/hazards/schedule.ts` (manifest v1 allocator: intro L10 Pulse Gate, L20 Sentry, L35 Hunter, L60 Shard; tail one unit every 15 levels from L36 to geometry saturation; caps 6/4/2/5; exposure stage) and `src/mazer-core/hazards/overlay.ts` (allocate, place with no blockers and Sentries off chokepoints, verdict at N = 2, escape slack >= 0.9 with no fragile step in the first 10, degrade one hazard at a time with a recorded reason). `src/legacy-runtime/legacyHazardOverlay.ts` is the legacy entry point: it returns null when `enabled` is false and never reads the maze then. `placeLevelHazards` gained the opt-in `patrolsAvoidChokepoints` (A6). Two perf changes in `solvability.ts`: a flat move table in the state space and `createSolvableQuery` (k = 0 layer solved once, k > 0 on demand), used by the validator and escape slack. Census: `scripts/analysis/hazard-overlay-census.ts`.
- WHY it changed: roadmap slice H2. Hazards must be proven deterministic, fair and inside the generation budget before anything is drawn (H3).
- Rule: the overlay only reads a finished maze. It has its own seed stream (`mix32(mazeSeed, level, scheduleVersion, "HAZD")`), so geometry, the solution path, the felt number and openings cannot move. Flag off, nothing runs.
- Rule: a Web Worker cannot read the query string or localStorage (GEN-020 trap). H3 must resolve the hazard switch on the main thread and pass `enabled` in the maze worker's job message, then run the overlay in the worker right after generation. The overlay's module graph has no Phaser or DOM import, so it can load in the worker.
- Rule (interface for H3/H6/H7, stable from this PR): call `resolveLegacyHazardOverlay(maze, { enabled, level, exposureStage? }): HazardOverlayResult | null` (null when off). `HazardOverlayResult` carries `status` ('none' | 'full' | 'degraded'), `specs: HazardSpec[]` (timedGate/patrol only, no blockers), `allocation: HazardAllocation` (counts, tiers, `firstEncounter`, `exposureStage`, `tailUnits`), `verdict: LevelHazardVerdict | null` (holds `witness` with `cells`/`ticks`), `escapeSlack`, `deferred` (hunters H5, shards H8), `degradeReasons` and `digest`. Core callers use `computeHazardOverlay(graph, { start, goal, mazeSeed, level, saturationLevel, exposureStage? })` and `allocateHazardUnits(level, { saturationLevel, exposureStage? })`. Changing any of these shapes is a contract change; say so in the PR.
- Evidence: census on the shipped ladder, node 1x on a desktop PC, overlay = graph build + allocation + placement + verdict + escape slack:
  - L10..300 every level, 2 seeds, phone and desktop (1164 runs): median 12.55 ms, p95 about 35 ms, worst 57.74 ms (budget 25 / 80). 1149 full, 15 degraded (fragile-early-step 13, escape-slack-low 3), 0 mazes changed, min escape slack 0.90.
  - L1..1000 every 3rd level, 3 seeds, both boards (2004 runs): median 15.99 ms, worst 67.46 ms; 1971 full, 15 degraded, 18 none (below L10), 0 mazes changed.
  - Off-ladder 1:1 board (`--boards=square`), L1..1000 every 3rd level, 3 seeds (1002 runs): median 13.10 ms, worst 57.44 ms; 991 full, 2 degraded, 9 none, 0 mazes changed, min escape slack 0.907.
  - L10..300 every 10th level, 2 seeds, with the felt number re-measured: 0 changed; median 11.19 ms, worst 52.85 ms.
  - Before the two solvability changes the same L10..300 sweep measured median 28.2 ms, worst 106.5 ms (over budget).
  - Tests: allocator pinned to the manifest JSON and re-derived independently; layered solvable query equals the full pass on every state of 18 random scenarios; real-maze checks with production movement and the brute-force oracle (contact-free solvability and witness length, junction rewind at N = 2 and N = 4, Sentry never on a chokepoint, escape slack re-measured exactly); golden progression-ladder parity unchanged.
