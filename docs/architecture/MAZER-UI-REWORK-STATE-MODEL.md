# Mazer UI Rework State Model

## Status

Wave 1A ("Shared state, commands, profiles, view models") completes the shared, renderer-independent foundation declared across `spec/ui-state-model.json`, `spec/platform-profiles.json`, `spec/component-registry.json`, and blueprint 03/06/08/09 in the authoritative `mazer-everything-bundle-20260803` handoff.

## Files

- `docs/contracts/mazer-ui-rework-state-model.v1.json` -- the single source of truth: primary surfaces, modal surfaces, game/auth/connection/install phases, control modes, motion modes, effects-quality tiers (reproduced from the bundle's `spec/ui-state-model.json`), plus the model's four `invariants` and a `structurallyCheckableInvariants` subset naming exactly which of those four this wave's TypeScript shape actually enforces by construction.
- `src/state/uiState.ts` -- typed TypeScript literal-union types for each category, the `UiStateSnapshot` interface, and `collectUiStateSnapshotViolations`, a runtime validator (typed to accept `unknown`, not just `UiStateSnapshot`) for snapshot-shaped values against the registered enums, useful once a real value needs checking rather than trusted at the type level alone. Fails closed on a malformed top-level value (`null`, `undefined`, or anything else that isn't an object) with a single sentinel-field violation instead of throwing, in addition to failing closed per-field via `memberCheck`.
- `src/state/uiCommands.ts` -- exhaustive discriminated command union, fail-closed runtime validator, and the actual subscribe/dispatch command bus for every command family named in blueprint 03.
- `src/state/uiStore.ts` -- immutable snapshot store; `dispatch` is the sole UI-owned state-transition path and every transition returns a validated frozen snapshot. Domain commands are emitted through the command bus but do not let a renderer invent game, auth, connection, or install results.
- `src/state/uiProfiles.ts` -- all seven authoritative output profiles and a fail-closed resolver. Auth and sync capability types are intentionally distinct; profiles vary capabilities/chrome, never brand identity.
- `src/state/uiViewModels.ts` -- immutable, geometry-free projections for the authoritative view-model families plus the current-main `LeaderboardViewModel` addendum.
- `src/state/uiLegacyProjection.ts` -- pure, renderer-independent projection seam from explicit legacy mode/overlay facts into a validated immutable snapshot.
- `scripts/check-ui-state-model.mjs` -- validates categories/invariants and exact authoritative command/view-model lists, cross-checks decisions, and applies dependency-ordered ownership without any stale pull-request exception.
- `tests/architecture/ui-state-model-contract.test.ts` -- runs the above checker against the real files, cross-checks `src/state/uiState.ts`'s exported category arrays against the JSON registry (values and order), asserts mutated copies of the registry are rejected for each rule, exercises the canonical snapshot and immutable command boundaries adversarially, and re-runs dependency-ordered `integratorWaveOwnership.assignments` checks (including a disposable-fixture regression proving a fully committed wrong-wave change is still caught even with a clean `git status --short`).

## Why "exactly-one-primary-surface" and "zero-or-one-modal" are structural, not just asserted

`UiStateSnapshot.primarySurface` and `.modalSurface` are each a single required field of one of the registered literal-union types (not an array, not optional). A well-typed `UiStateSnapshot` value therefore cannot have zero or multiple primary surfaces, and `modalSurface` is always present with `'none'` as the explicit zero-modal member -- so both invariants hold by TypeScript's type system alone, for any value that type-checks. The other two invariants in the JSON (`modal-focus-trap`, `domain-state-not-mutated-by-renderers`) are behavioral properties of whatever eventually *consumes* this snapshot (a real DOM/Phaser adapter with actual focus management and actual renderer wiring), not properties the snapshot shape itself can guarantee -- they are listed in `invariants` as documented commitments for later waves to honor, but deliberately left out of `structurallyCheckableInvariants`, and `scripts/check-ui-state-model.mjs` fails if that boundary is blurred (e.g. if the JSON's `structurallyCheckableInvariants` ever grows to claim more than this wave's code actually enforces without someone updating both together).

## Fitness pattern intake

- `ADOPT` one-overlay/recoverable interaction: owner `UiStore`; proved by command/store architecture tests.
- `ADAPT` accessible motion preferences: owner `UiStateSnapshot`/view models; proved as semantic state only, with visual behavior deferred to renderer waves.
- `ADOPT` versioned explainable persistent state: owner shared state contract; no persistence write is added in this wave.
- `NOT_APPLICABLE` safe areas, persistent bottom controls, responsive layout, install capability, and served-build provenance: their runtime owners are later layout/system/release waves; this source-only foundation neither copies Fitness UI nor claims route-level proof.

## Wave 3A -- live command/state bridge

Wave 3A (owner `command-bridge-integrator`, path `src/scenes/MenuScene.ts` per `integratorWaveOwnership`) makes the Wave 1A foundation above load-bearing against the real running scene.

- **Bridge location**: `src/state/uiLegacyBridge.ts` (`UiLegacyBridge`). Not locked to any wave's exclusive path -- lives alongside the other `src/state/*` foundation modules it composes, rather than inside `MenuScene.ts` itself, so it stays testable with a plain fake adapter and no Phaser import. `MenuScene.ts` is the sole real call site: it constructs one instance in `create()` (`this.uiBridge`), destroys it on scene shutdown, and is the only file that supplies a real `UiLegacyBridgeAdapter`.
- **Source-of-truth direction**: the legacy runtime remains authoritative. `getSnapshot()`/`getViewModels()` are always derived fresh from real legacy facts via `projectLegacyUiState()` -- never from `uiStore`'s own reducer, which intentionally no-ops most runtime/domain commands (start, pause, resume, reset, auth, install, directional input). The bridge uses `createUiCommandBus()` (validation + a post-hoc "what actually happened" event) rather than `createUiStore()`, specifically so no second, independently-mutated snapshot can exist to drift from the live scene.
- **Command mapping**: `UiLegacyBridge.dispatch()` maps each `UiCommand` type to an existing MenuScene method through the adapter (`openOverlay`, `closeOverlay`/`handleBackAction`, `startPlayMode`, `applyLegacyPauseCommand`, `resetLegacyPlayerProgression`, `enterMenuMode`, `handleLegacyAuthSignOut`) -- it adds no new runtime behavior, only names the seam. `NAVIGATE`/`OPEN_MODAL` cover `home`/`account`/`settings`/`leaderboard`/`confirm-reset-progress`; other `PrimarySurfaceLiteral`/`ModalSurfaceLiteral` values (`guide`, `result`, `system-error`, `watch-pass-*`, `boot`, the remaining modals) have no live surface yet and fail closed with an explicit `{ ok: false, reason }` rather than silently no-op-ing. `SET_CONTROL_MODE`, `SET_PREFERENCE`, `INSTALL_APP`/`DISMISS_INSTALL`/`APPLY_UPDATE`/`RETRY_SYSTEM_ACTION`, `SUBMIT_AUTH`, and both directional-intent commands are deliberately left unimplemented in the current adapter (omitted, not stubbed) pending a real settings/install/auth-entry seam -- dispatching them fails closed with an `*-unsupported` reason today.
- **Projection mapping**: `resolveUiBridgeFacts()` in `MenuScene.ts` supplies `mode`/`overlay`/`overlayReturn` (real), `authPhase` (real, from `authSnapshot.status`), `controlMode` (real, from `settings.controlMode`), and `motionMode` (real, from `prefers-reduced-motion`). `gamePhase` is a disclosed simplification (`paused`/`active`/`idle` only -- no live `generating`/`preroll`/`complete` signal is wired in yet); `connectionPhase` (`'online'`) and `installPhase` (`'hidden'`) are fixed placeholders pending a real live signal; `effectsQuality` (`'balanced'`) has no backing runtime setting at all yet. `projectLegacyUiState()` itself was corrected this wave: `confirm-progression-reset` now reads `overlayReturn` to keep the surface it actually opened from (`account` or `play`, matching `MenuScene`'s two real `openOverlay('confirm-progression-reset')` call sites) instead of falling through to a generic `home` default.
- **Diagnostics**: `UiLegacyBridge.getDiagnostics()` exposes `installed`, `projectionRevision`, `dispatchCount`, `lastCommandType`, `lastRefreshReason`, `currentSnapshot`, `visibleViewModelNames`, `projectionViolationCount`, `commandFailureCount`, `destroyed` -- no credentials or auth payloads. Reachable under `runtimeDiagnostics=1` via `window.__MAZER_QA__.getUiBridgeDiagnostics()` / `getUiStateSnapshot()` / `getUiViewModels()` / `dispatchUiCommand()`, all calling the one real installed instance, not a test-only duplicate.
- **Lifecycle boundary**: `refreshProjection(reason)` is called at `bridge-installation`, every `openOverlay()`/`closeOverlay()` (`overlay-open`/`overlay-close`), `enterMenuMode()`/`startPlayMode()` (`mode-change`), `applyLegacyAuthSnapshot()` (`auth-change`), and on each successful `dispatch()` (`command:<TYPE>`) -- deduplicated by a facts-equality check so an unchanged tick does not allocate a new snapshot or bump `projectionRevision`. The pre-existing progression-reset origin/native-input-cleanup fix (see the `fix(ui): preserve reset-confirmation origin and clean native inputs` commit) is the first real acceptance slice this lifecycle boundary depends on.
- **Verified**: full `npm run verify` (774 tests across 87 files + 12 fork-pool tests + production build) passes with the bridge installed; `tests/architecture/ui-legacy-bridge.test.ts` (15 tests, fake-adapter unit coverage) and the extended `ui-state-model-contract.test.ts`/`legacy-overlay-routing.test.ts` origin-aware projection/routing cases are new this wave.
- **Known deferred work (Wave 3B/3C/4D)**: `SUBMIT_AUTH`/`LOG_OUT`'s deeper auth-domain behavior remains Wave 3B's (`src/legacy-runtime/legacyAuth.ts`/`legacyPlayerMessage.ts`), not touched here. Real `gamePhase`/`connectionPhase`/`installPhase`/`effectsQuality`/`SET_CONTROL_MODE`/`SET_PREFERENCE`/directional-intent/install-command wiring needs either a later wave's new settings/install surface or an explicit decision to extend this wave's scope. Only the reset-confirmation and a handful of lifecycle call sites route through the bridge today; the remaining named UI entry points (general Start/Settings/Account/Leaderboard button clicks beyond what already called `openOverlay`/`startPlayMode` directly) still call the underlying methods directly rather than `bridge.dispatch()` -- converting them is mechanical (the adapter methods already exist) but was not exhaustively swept across the full `MenuScene.ts` file this pass. Wave 4D-A (Navigation Core runtime) is unaffected by and does not depend on this bridge.
