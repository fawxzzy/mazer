# Mazer UI Rework State Model

## Status

Wave 1A ("State/commands/view models") of the Mazer UI rework, per `blueprint/09_MIGRATION_WAVES_AND_PR_LANES.md` in the `mazer-everything-bundle-20260803` authoritative handoff. Per `spec/pr-lanes.json`, lane 1A is `parallel: yes` with `exclusiveFiles: ["shared contract exports"]` -- it is independent of PR #83's collision files and does not require PR #83 (Wave 0B) to be reconciled first. This PR delivers the `spec/ui-state-model.json` piece of that lane (the renderer-independent UI state snapshot); the "commands" and "view models" pieces the lane name also references have no concrete spec file in the handoff bundle and are left for a follow-on, since inventing their shape without a source-of-truth spec would not be "registering" anything, it would be authoring new design.

This wave registers and contract-tests the state model; it does **not** wire it into `index.html`, `vite.config.ts`, `src/scenes/MenuScene.ts`, or any other live-render path, and it does **not** map any of `MenuScene.ts`'s actual current state into this shape. `src/scenes/MenuScene.ts`, `src/scenes/menuRuntimeDiagnostics.ts`, `src/legacy-runtime/legacyAuth.ts`, `src/legacy-runtime/legacyPlayerMessage.ts`, the three `scripts/analysis/*capture*` scripts, `vite.config.ts`, and `package.json` remain untouched -- they are `prProtection.protectedPaths` in `docs/contracts/mazer-ui-rework-decision-registry.v1.json`, held for PR #83's Wave 0B integrator-exclusive reconciliation. Mapping real legacy state into this snapshot shape is later wave work (Wave 3A, "Command bridge/state projection", which is itself `exclusiveFiles: ["MenuScene.ts"]` and therefore also integrator-gated).

## Files

- `docs/contracts/mazer-ui-rework-state-model.v1.json` -- the single source of truth: primary surfaces, modal surfaces, game/auth/connection/install phases, control modes, motion modes, effects-quality tiers (reproduced from the bundle's `spec/ui-state-model.json`), plus the model's four `invariants` and a `structurallyCheckableInvariants` subset naming exactly which of those four this wave's TypeScript shape actually enforces by construction.
- `src/state/uiState.ts` -- typed TypeScript literal-union types for each category, the `UiStateSnapshot` interface, and `collectUiStateSnapshotViolations`, a runtime validator for snapshot-shaped values against the registered enums (useful once a real value needs checking rather than trusted at the type level alone).
- `scripts/check-ui-state-model.mjs` -- validates the JSON registry's internal shape (every category non-empty with no duplicate/non-string entries, `modalSurfaces` includes `"none"`, `structurallyCheckableInvariants` is a subset of `invariants` and contains the two entries this wave claims to enforce), cross-checks `decisionRefs` against `docs/contracts/mazer-ui-rework-decision-registry.v1.json`, and re-exports the PR #83/#82 protected-path self-check via `readGitChangedFilesForStateModel`, which delegates to `scripts/check-decision-registry.mjs`'s `readGitChangedFiles` (committed-diff-aware, not `git status --short` alone -- see that module for why).
- `tests/architecture/ui-state-model-contract.test.ts` -- runs the above checker against the real files, cross-checks `src/state/uiState.ts`'s exported category arrays against the JSON registry (values and order), asserts mutated copies of the registry are rejected for each rule, exercises `collectUiStateSnapshotViolations` against both a fully valid and a deliberately invalid snapshot, and re-runs the PR #83/#82 protected-path self-check (including a disposable-fixture regression proving a fully committed protected-path change is still caught even with a clean `git status --short`).

## Why "exactly-one-primary-surface" and "zero-or-one-modal" are structural, not just asserted

`UiStateSnapshot.primarySurface` and `.modalSurface` are each a single required field of one of the registered literal-union types (not an array, not optional). A well-typed `UiStateSnapshot` value therefore cannot have zero or multiple primary surfaces, and `modalSurface` is always present with `'none'` as the explicit zero-modal member -- so both invariants hold by TypeScript's type system alone, for any value that type-checks. The other two invariants in the JSON (`modal-focus-trap`, `domain-state-not-mutated-by-renderers`) are behavioral properties of whatever eventually *consumes* this snapshot (a real DOM/Phaser adapter with actual focus management and actual renderer wiring), not properties the snapshot shape itself can guarantee -- they are listed in `invariants` as documented commitments for later waves to honor, but deliberately left out of `structurallyCheckableInvariants`, and `scripts/check-ui-state-model.mjs` fails if that boundary is blurred (e.g. if the JSON's `structurallyCheckableInvariants` ever grows to claim more than this wave's code actually enforces without someone updating both together).

## Why this is safe to land independently of PR #83 / Wave 0B

- No file this wave adds or edits appears in `prProtection.protectedPaths`; the test suite re-asserts this against the real working tree's committed-and-uncommitted changed files, the same pattern Wave 0A's `decision-registry-contract.test.ts` and Wave 1B's `design-tokens-contract.test.ts` established (as of this wave, using the corrected committed-diff-aware implementation, not the git-status-only one those two waves originally shipped with).
- Nothing is imported by a live entrypoint (`index.html`, `proof-surfaces.html`, etc.) or by `vite.config.ts`'s build input map, so there is no visual or behavioral change to verify beyond "the new files exist, are internally consistent, and type-check."
- `docs/contracts/mazer-ui-rework-decision-registry.v1.json` already locks `renderer-ownership-split` and `no-big-bang-menuscene-rewrite`; this wave's `decisionRefs` point at those same two decisions rather than inventing new ones, keeping one registry of decisions.

## Non-goals of this wave

This wave does not map any real `MenuScene.ts` state into `UiStateSnapshot`, does not define "commands" (the action/intent side of the state model) or view models (derived, renderer-specific projections of a snapshot) -- both remain unspecified in the handoff bundle beyond the lane name itself, and are left for a follow-on with either a concrete spec to register or an explicit design decision to make first. It also does not begin DOM extraction or command-bridge wiring -- those are Waves 2A and 3A.
