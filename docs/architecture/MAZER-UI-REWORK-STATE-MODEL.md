# Mazer UI Rework State Model

## Status

Wave 1A ("Shared state, commands, profiles, view models") completes the shared, renderer-independent foundation declared across `spec/ui-state-model.json`, `spec/platform-profiles.json`, `spec/component-registry.json`, and blueprint 03/06/08/09 in the authoritative `mazer-everything-bundle-20260803` handoff.

This wave does **not** wire the foundation into `index.html`, `vite.config.ts`, `src/scenes/MenuScene.ts`, Phaser, or DOM APIs. `uiLegacyProjection.ts` is a pure mapping contract and fixture seam; mapping the live scene and making the command bridge load-bearing remains Wave 3A. The former PR #83/#131 branch hold is retired; dependency-ordered registry ownership now protects the shared paths.

## Files

- `docs/contracts/mazer-ui-rework-state-model.v1.json` -- the single source of truth: primary surfaces, modal surfaces, game/auth/connection/install phases, control modes, motion modes, effects-quality tiers (reproduced from the bundle's `spec/ui-state-model.json`), plus the model's four `invariants` and a `structurallyCheckableInvariants` subset naming exactly which of those four this wave's TypeScript shape actually enforces by construction.
- `src/state/uiState.ts` -- typed TypeScript literal-union types for each category, the `UiStateSnapshot` interface, and `collectUiStateSnapshotViolations`, a runtime validator (typed to accept `unknown`, not just `UiStateSnapshot`) for snapshot-shaped values against the registered enums, useful once a real value needs checking rather than trusted at the type level alone. Fails closed on a malformed top-level value (`null`, `undefined`, or anything else that isn't an object) with a single sentinel-field violation instead of throwing, in addition to failing closed per-field via `memberCheck`.
- `src/state/uiCommands.ts` -- exhaustive discriminated command union, fail-closed runtime validator, and the actual subscribe/dispatch command bus for every command family named in blueprint 03.
- `src/state/uiStore.ts` -- immutable snapshot store; `dispatch` is the sole UI-owned state-transition path and every transition returns a validated frozen snapshot. Domain commands are emitted through the command bus but do not let a renderer invent game, auth, connection, or install results.
- `src/state/uiProfiles.ts` -- all seven authoritative output profiles and a fail-closed resolver. Auth and sync capability types are intentionally distinct; profiles vary capabilities/chrome, never brand identity.
- `src/state/uiViewModels.ts` -- immutable, geometry-free projections for the authoritative view-model families plus the current-main `LeaderboardViewModel` addendum.
- `src/state/uiLegacyProjection.ts` -- pure, renderer-independent projection seam from explicit legacy mode/overlay facts into a validated immutable snapshot.
- `scripts/check-ui-state-model.mjs` -- validates categories/invariants and exact authoritative command/view-model lists, cross-checks decisions, and applies dependency-ordered ownership without any stale pull-request exception.
- `tests/architecture/ui-state-model-contract.test.ts` -- runs the above checker against the real files, cross-checks `src/state/uiState.ts`'s exported category arrays against the JSON registry (values and order), asserts mutated copies of the registry are rejected for each rule, exercises the canonical snapshot and immutable command boundaries adversarially, and re-runs dependency-ordered `integratorWaveOwnership.assignments` checks (including a disposable-fixture regression proving a fully committed wrong-wave change is still caught even with a clean `git status --short`).

## Why "exactly-one-primary-surface" and "zero-or-one-modal" are structural, not just asserted

`UiStateSnapshot.primarySurface` and `.modalSurface` are each a single required field of one of the registered literal-union types (not an array, not optional). A well-typed `UiStateSnapshot` value therefore cannot have zero or multiple primary surfaces, and `modalSurface` is always present with `'none'` as the explicit zero-modal member -- so both invariants hold by TypeScript's type system alone, for any value that type-checks. The other two invariants in the JSON (`modal-focus-trap`, `domain-state-not-mutated-by-renderers`) are behavioral properties of whatever eventually *consumes* this snapshot (a real DOM/Phaser adapter with actual focus management and actual renderer wiring), not properties the snapshot shape itself can guarantee -- they are listed in `invariants` as documented commitments for later waves to honor, but deliberately left out of `structurallyCheckableInvariants`, and `scripts/check-ui-state-model.mjs` fails if that boundary is blurred (e.g. if the JSON's `structurallyCheckableInvariants` ever grows to claim more than this wave's code actually enforces without someone updating both together).

## Fitness pattern intake

- `ADOPT` one-overlay/recoverable interaction: owner `UiStore`; proved by command/store architecture tests.
- `ADAPT` accessible motion preferences: owner `UiStateSnapshot`/view models; proved as semantic state only, with visual behavior deferred to renderer waves.
- `ADOPT` versioned explainable persistent state: owner shared state contract; no persistence write is added in this wave.
- `NOT_APPLICABLE` safe areas, persistent bottom controls, responsive layout, install capability, and served-build provenance: their runtime owners are later layout/system/release waves; this source-only foundation neither copies Fitness UI nor claims route-level proof.

## Wave 3A -- live command/state bridge

Wave 3A (owner `command-bridge-integrator`, paths `src/scenes/MenuScene.ts` and `src/state/uiLegacyBridge.ts` per `integratorWaveOwnership`) makes the Wave 1A foundation above load-bearing against the real running scene.

- **Bridge location**: `src/state/uiLegacyBridge.ts` (`UiLegacyBridge`), explicitly registered under this wave's own path list. Lives alongside the other `src/state/*` foundation modules it composes, rather than inside `MenuScene.ts` itself, so it stays testable with a plain fake adapter and no Phaser import. `MenuScene.ts` is the sole real call site: it constructs one instance in `create()` (`this.uiBridge`), destroys it on scene shutdown, and is the only file that supplies a real `UiLegacyBridgeAdapter`.
- **Source-of-truth direction**: the legacy runtime remains authoritative. `getSnapshot()` always re-reads real legacy facts via `refreshProjection()` (deduplicated by a facts-equality check, so a caller that forgets to call it explicitly after some transition still sees current state, not stale cache) -- never `uiStore`'s own reducer, which intentionally no-ops most runtime/domain commands. The bridge uses `createUiCommandBus()` (validation + a post-hoc "what actually happened" event), not `createUiStore()`, so no second, independently-mutated snapshot can exist to drift from the live scene.
- **Command mapping**: `UiLegacyBridge.dispatch()` maps each `UiCommand` type to an existing MenuScene method (or a real boot-time seam, for install commands) through the adapter -- it adds no new runtime behavior, only names the seam, and adapter actions return `boolean` where the real operation can be rejected (not `void` always treated as success). Wired with a real seam: `NAVIGATE` (`home`/`account`/`settings`/`leaderboard`), `OPEN_MODAL confirm-reset-progress` (validates the live overlay is actually `auth` or `pause` before opening -- rejects any other origin explicitly instead of defaulting to Account), `CLOSE_MODAL`, `START_RUN`/`PAUSE_RUN`/`RESUME_RUN`/`RESET_RUN`/`RESET_PROGRESS`/`RETURN_HOME` (each with a real accept/reject guard, e.g. `startRun` checks `hasLegacyPlayAccess()`), `SET_CONTROL_MODE` (real `stick`/`arrows` toggle), `INSTALL_APP`/`DISMISS_INSTALL` (the real `src/boot/installSurface.ts` module), `DISPATCH_DIRECTIONAL_INTENT` (the real QA move surface), `LOG_OUT`. Left unimplemented (omitted, not stubbed) pending a real seam: `CANCEL_GENERATION` (no independent generation-cancellation exists in the runtime today -- deliberately not mapped to closing an overlay), `SET_PREFERENCE`, `SUBMIT_AUTH`, `APPLY_UPDATE`, `RETRY_SYSTEM_ACTION`, `RELEASE_DIRECTIONAL_INTENT`; other `PrimarySurfaceLiteral`/`ModalSurfaceLiteral` values with no live surface (`guide`, `result`, `system-error`, `watch-pass-*`, `boot`, other modals) also fail closed. All of the above return an explicit `{ ok: false, reason }` rather than silently no-op-ing or reporting a false success.
- **Projection mapping**: `resolveUiBridgeFacts()` in `MenuScene.ts` supplies `mode`/`overlay`/`overlayReturn` (real), `authPhase` (real, the full `LegacyAuthStatus` domain), `controlMode` (real, `settings.controlMode`), `motionMode` (real, `prefers-reduced-motion`), `installPhase` (real, the live `src/boot/installSurface.ts` state), and `gamePhase` (real: `menuStaticDrawLifecyclePhase`/`playCompletedAtMs`/`isLegacyPlayLifecycleInputLocked()` cover `generating`/`paused`/`complete`/`input-locked`/`active`/`idle`). `connectionPhase` and `effectsQuality` have no real distinct live signal in the runtime at all and are named in `LegacyRuntimeFacts.placeholderFields`, surfaced honestly via `getDiagnostics().placeholderFacts` rather than presented as real projected state. The platform profile passed to the bridge is resolved from a real touch-capability check (`navigator.maxTouchPoints`), not always `PLATFORM_PROFILES.web`. `projectLegacyUiState()` itself was corrected this wave: `confirm-progression-reset` now reads `overlayReturn` to keep the surface it actually opened from (`account` or `play`) instead of falling through to a generic `home` default.
- **Diagnostics**: `UiLegacyBridge.getDiagnostics()` exposes `installed`, `projectionRevision`, `dispatchCount`, `lastCommandType`, `lastRefreshReason`, `currentSnapshot`, `visibleViewModelNames`, `projectionViolationCount`, `commandFailureCount`, `placeholderFacts`, `destroyed` -- no credentials or auth payloads. Reachable under `runtimeDiagnostics=1` via `window.__MAZER_QA__.getUiBridgeDiagnostics()` / `getUiStateSnapshot()` / `getUiViewModels()` / `dispatchUiCommand()`, all calling the one real installed instance, not a test-only duplicate -- proven against a real build in `scripts/analysis/verify-ui-bridge-integration.mjs` (see Verified below).
- **Lifecycle boundary**: `refreshProjection(reason)` is called at `bridge-installation`, every `openOverlay()`/`closeOverlay()` (`overlay-open`/`overlay-close`), `enterMenuMode()`/`startPlayMode()` (`mode-change`), `applyLegacyAuthSnapshot()` (`auth-change`), and on each successful `dispatch()` (`command:<TYPE>`); `getSnapshot()`'s own always-re-read behavior makes a forgotten call site non-fatal rather than a source of stale state. Live UI entry points routed through `bridge.dispatch()` (via `MenuScene.dispatchUiBridgeCommand()`, falling back to the direct low-level call only if the bridge rejects or is unavailable, never recursing back into the bridge): the front-door Login/Start/Settings-cog/Leaderboard/Profile buttons, the Options-overlay and forced-auth-gate "Go to Account" buttons, the Pause overlay's back-chevron (resume) and home (return-menu) buttons, and the Account screen's "Reset progress" link. The progression-reset origin/native-input-cleanup fix (see the `fix(ui): preserve reset-confirmation origin and clean native inputs` commit) is the first real acceptance slice this lifecycle boundary depends on.
- **Verified**: full `npm run verify` (774 tests across 87 files + 12 fork-pool tests + production build) passes with the bridge installed; `tests/architecture/ui-legacy-bridge.test.ts` (23 tests, fake-adapter unit coverage including both `OPEN_MODAL` origins, the invalid-origin rejection, `CANCEL_GENERATION` failing closed, adapter-rejection propagation, and stale-snapshot prevention) and the extended `ui-state-model-contract.test.ts`/`legacy-overlay-routing.test.ts`/`decision-registry-contract.test.ts` cases are new this wave. `scripts/analysis/verify-ui-bridge-integration.mjs` is real browser integration evidence (not a fake adapter) against this branch's own production build: confirms the bridge is installed on real boot, a real access-denied `START_RUN` is rejected (not falsely accepted), a real authenticated `START_RUN` is accepted and the real scene actually reaches unlocked play mode (confirmed via the independent QA move surface), the projected snapshot/view model change accordingly, an unsupported command fails closed, and `OPEN_MODAL confirm-reset-progress` rejects an invalid live origin -- run it with `node scripts/analysis/verify-ui-bridge-integration.mjs`.
- **Known deferred work (Wave 3B/3C/4D)**: `SUBMIT_AUTH`/`LOG_OUT`'s deeper auth-domain behavior remains Wave 3B's (`src/legacy-runtime/legacyAuth.ts`/`legacyPlayerMessage.ts`, not touched here); `SUBMIT_AUTH` specifically needs its shared `{intent, payload}` shape reconciled with `authForm`'s field-population flow, which needs its own careful pass given the sensitivity of auth code, so it is left unimplemented rather than wired approximately. `SET_PREFERENCE` (`motionMode`/`effectsQuality`), `CANCEL_GENERATION`, `APPLY_UPDATE`, `RETRY_SYSTEM_ACTION`, and `RELEASE_DIRECTIONAL_INTENT` have no real runtime seam identified yet. Not every UI entry point routes through the bridge yet -- e.g. in-play touch/keyboard movement itself still uses its existing internal mechanics directly (as intended; only the shared `DISPATCH_DIRECTIONAL_INTENT` command path was wired for future DOM controls to consume, not a rewrite of the movement system). Wave 4D-A (Navigation Core runtime) is unaffected by and does not depend on this bridge.
