# Mazer UI Rework Topology/Path Contract

## Status

Wave 2B ("Topology/path geometry") of the Mazer UI rework, per `blueprint/09_MIGRATION_WAVES_AND_PR_LANES.md` in the `mazer-everything-bundle-20260803` authoritative handoff ("PR 2B -- Topology/path geometry source: Pure modules and tests. No shipping renderer switch yet."). Per `spec/pr-lanes.json`, lane 2B is `parallel: yes` with `exclusiveFiles: ["geometry/render sources"]` -- new files only, independent of PR #83's collision files, and does not require Wave 1C ("Diagnostics split") to land first, since 2B does not touch or depend on diagnostics files at all.

This PR delivers the one concrete spec file the handoff bundle provides for this lane, `spec/topology-path-contract.json` (the 16-mask connected-corridor bit/connection contract). It does **not** implement actual rendering math (corridor segment coordinates, corner/border geometry, or any drawing code) -- that is Wave 4D's job ("Board/title path renderer", `exclusiveFiles: ["board render/title render"]`), which is itself gated behind Wave 3A's command-bridge work. This wave registers and contract-tests the pure bit/mask/connection vocabulary only.

## Why Wave 2B, not Wave 1C

Wave 1 has one remaining lane, 1C ("Diagnostics schema split"). It was not picked up by this pass for two independent reasons, either of which alone would be sufficient:

1. **No concrete spec file.** Unlike 1A (`spec/ui-state-model.json`) and 1B (`spec/design-tokens.json`), the handoff bundle's `spec/` directory has no diagnostics-schema JSON backing 1C's "Diagnostics schema split" name -- only the lane name itself. Inventing a diagnostics schema shape without a source-of-truth spec would be authoring new design, not registering something the bundle already specifies -- the same reasoning Wave 1A's own documentation gave for leaving "commands" and "view models" unregistered.
2. **File-scope collision.** `spec/pr-lanes.json` lane 1C is `"parallel with integrator"` with `exclusiveFiles: ["diagnostics owners"]`, and `blueprint/09_MIGRATION_WAVES_AND_PR_LANES.md`'s file-ownership guardrails table lists `src/scenes/menuRuntimeDiagnostics.ts and successors` as a single-owner/integrator surface -- the same file named in `docs/contracts/mazer-ui-rework-decision-registry.v1.json`'s live `prProtection.protectedPaths` and in this task's own off-limits list (it is part of PR #131's file scope). 1C cannot be done by a non-integrator lane right now regardless of spec availability.

Wave 2's three lanes (2A DOM foundation, 2B topology/path geometry, 2C asset/icon generator) are listed as `parallel: yes` in both `spec/pr-lanes.json` and `matrices/PR_LANES.csv`, with no stated dependency on 1C completing first -- Wave 1's three lanes are each independent "Contracts and tokens" registrations, not sequential prerequisites of each other. Of Wave 2's three lanes, 2B is the only one backed by a single, complete, concrete spec file (`spec/topology-path-contract.json` -- 16 fully-enumerated masks with an unambiguous bit/connection definition). 2A's only bundle artifact, `spec/component-registry.json`, is a bare list of component *names* with no prop/behavior schema -- building real DOM components from names alone would mean inventing their shape, the same trap this wave avoids for 1C. 2C ("Asset/icon generator") has no spec file in the bundle at all. 2B was picked as the one lane this pass could implement as registration of an existing spec, not invention of new design.

## Files

- `docs/contracts/mazer-ui-rework-topology-path-contract.v1.json` -- the single source of truth: the `bits` map (`N=1, E=2, S=4, W=8`), the canonical `shippingPresentation` (`"connected-corridor"`), the non-shipping `debugPresentations` (`cell-outline`, `centerline`, `mask-label`), and all 16 `masks` entries (mask value 0-15 plus its connection list), reproduced verbatim from the bundle's `spec/topology-path-contract.json` (byte-for-byte identical on the `bits`/`shippingPresentation`/`debugPresentations`/`masks` fields, confirmed by a direct JSON diff during this wave's self-review).
- `src/geometry/topologyPath.ts` -- hand-authored TypeScript constants (`DIRECTIONS`, `DIRECTION_BITS`, `TOPOLOGY_MASKS`) independent of the JSON import (not cast from it, following Wave 1A's documented lesson about vacuous `as`-cast cross-checks), plus pure functions: `maskConnections` (mask -> ordered direction list, computed by bitwise test), `connectionsToMask` (the inverse), `hasConnection`, `isValidTopologyMask` (a runtime guard over `unknown`, mirroring `collectUiStateSnapshotViolations`'s pattern), and `OPPOSITE_DIRECTION` (a minimal geometric primitive: N<->S, E<->W).
- `scripts/check-topology-path-contract.mjs` -- validates the JSON registry's internal shape: `bits` is exactly `{N:1,E:2,S:4,W:8}`; all 16 masks are present, unique, and in range; each mask's `connections` list is independently recomputed from `bits` via bit decomposition and compared against the JSON's own `connections` field (catching a typo in either representation); `shippingPresentation`/`debugPresentations` are well-formed and disjoint from each other; `decisionRefs` cross-check against `docs/contracts/mazer-ui-rework-decision-registry.v1.json`; and the PR #83/#82 protected-path self-check via `readGitChangedFilesForTopologyPathContract`, delegating to `scripts/check-decision-registry.mjs`'s committed-diff-aware `readGitChangedFiles`.
- `tests/architecture/topology-path-contract.test.ts` -- runs the checker against the real files; asserts mutated copies of the registry are rejected for each rule; cross-checks `src/geometry/topologyPath.ts`'s `maskConnections(mask)` output against the JSON's `masks[].connections` for all 16 masks individually (a genuinely independent comparison, since `DIRECTION_BITS` is hand-authored in the TS module, not imported from the JSON); round-trips `connectionsToMask(maskConnections(mask)) === mask` for all 16 masks; exercises `isValidTopologyMask` against valid and invalid inputs; and re-runs the PR #83/#82 protected-path self-check (including the disposable-fixture regression proving a fully committed protected-path change is still caught even with a clean `git status --short`).

## Relationship to existing, unrelated "topology" code in this repo

This wave's contract is unrelated to two other things already named "topology" in this repository, and does not modify either:

- `docs/architecture/MAZER-EDGE-WRAP-TOPOLOGY-CONTRACT.md` governs generated-maze *edge-wrap endpoint pairing* (a maze-generation concern: which border cells connect across a wrap, and how the generator/playable graph reconcile). This wave's contract is a *rendering* mask vocabulary (which of N/E/S/W a single cell's corridor connects to) -- a different layer entirely, consumed by a renderer, not by maze generation.
- `src/future-runtime/phaser/topology.ts` is a fixed, hand-authored tile graph for the unrelated `future-phaser.html` satellite-prototype lab surface (`retire-after-adapter-extraction` per decision `future-phaser-retire-after-adapter-extraction`), not a generic mask/connection contract.

## Why this is safe to land independently of PR #83 / Wave 0B / Wave 1C

- No file this wave adds appears in `prProtection.protectedPaths`; the test suite re-asserts this against the real working tree's committed-and-uncommitted changed files, the same pattern Wave 0A/1A/1B established.
- Nothing is imported by a live entrypoint (`index.html`, etc.), by `vite.config.ts`'s build input map, by `src/scenes/MenuScene.ts`, or by any existing board/renderer code -- there is no visual or behavioral change to verify beyond "the new files exist, are internally consistent, and type-check."
- `docs/contracts/mazer-ui-rework-decision-registry.v1.json` already locks `shipping-corridor-not-tiles` and `renderer-ownership-split`; this wave's `decisionRefs` point at those same two decisions rather than inventing new ones.

## Non-goals of this wave

This wave does not implement corridor rendering math (pixel/coordinate geometry, corner rounding, decorative cutouts -- those belong to `decorativeCutoutCandidates`/`decorativeCutoutPolicy` in the *unrelated* edge-wrap contract's renderer-mask-owned notch handling, or to Wave 4D generally), does not wire `src/geometry/topologyPath.ts` into any Phaser or future DOM renderer, does not touch `src/future-runtime/phaser/topology.ts`, and does not begin DOM extraction (Wave 2A) or command-bridge wiring (Wave 3A). It is registration and pure-function contract plumbing only.
